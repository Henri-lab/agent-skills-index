# 知识演化策略（knowledge evolution，唯一权威）

> 这套仓库的"利害 / 档位 / 坑"从经验起步，靠**使用回填**变准——本文定义回填与提升的规则，
> 让 agent 自己知道知识怎么升级。各技能的 lessons-log / maintenance 只保留入口，规则不复制。

## 1. 闭环

```
使用 → 记录（lessons-log，含"实际代价"）→ 聚类（同主题 ≥2）
     → 提升（决策表 / 协议）→ 复核（concept-map 一致）→ 再使用
```

## 2. 证据等级（决定一条回填值不值得提升）

真实项目事故 > 压测/基准数据 > 真实使用观察 > 文献推理。
**一条真实反例胜过十条推理**；一篇新文章只算"待验证假设"，不被实战印证前不进决策表。

## 3. 各层提升规则

| 素材 | 记录到 | 提升到 | 条件 |
| --- | --- | --- | --- |
| 单次踩坑 | 领域 lessons-log / engineering-pitfalls E-xxx | pitfalls / 决策表"代价"列 | 记录随时；提升需 ≥2 条同主题或一条事故 |
| 决策回填（选型结果） | lessons-log（模板见 §4） | stack-interview / solution-tiers 的"适合/代价" | ≥2 个项目同结论，或一条反例推翻 |
| 跨技能原则 | 对应技能 maintenance | agent-skills-index conventions | 两个以上技能都需要时 |
| 协议级（INV/OP/状态机） | ADR | MSP/ASP 正文 | 行为契约变化；只做加法 |

## 4. 决策回填模板（每个项目做完写一条）

```text
决策点：<语言 / 数据库 / 事件 / 缓存 / 部署 / CI 观测>
当时选择：<X>
当时理由：<…>
实际结果：<成 / 败 / 部分>
实际代价：<具体，可量化优先>
是否改变建议：<否 / 是 → 新建议>
来源：<项目名 + 日期>
```

## 5. 更新决策表的三条纪律

1. 只改"适合 / 代价"，不借机改协议语义（协议改动走 ADR）；
2. 改完同步 concept-map 的引用一致性；引用处只更新指针，不复制语义；
3. 被推翻的旧条目标 `[deprecated by …]` 保留溯源，不删除。

## 6. 触发条件（何时值得提升）

- 同主题 ≥2 条一致结论；
- 一条真实事故 / 资损；
- 一次压测或基准数据；
- 新文献 → 只作待验证假设，不进决策表。
